# ESP32-WROOM Telematics — MQTT Topics Reference

## Broker

| Parameter | Value |
|-----------|-------|
| Host | `broker.hivemq.com` |
| Port | `1883` (plain MQTT, no TLS) |
| Client ID | `smartwheels-wroom-ecu1` |
| Auth | None (public broker) |

---

## Topics Overview

| Direction | Topic | Purpose |
|-----------|-------|---------|
| Publish | `SmartKit/Ultra` | CAN signal data from MCU (or dummy data) |
| Publish | `SmartKit/device_health` | Device heartbeat / diagnostics |
| Subscribe | `SmartKit/Control` | Incoming commands from cloud → forwarded to MCU via UART1 |

---

## Publish: CAN Signals → `SmartKit/Ultra`

Published whenever a signal is received from the MCU over UART1, or generated by the dummy data engine.

**QoS:** 1 &nbsp;|&nbsp; **Retain:** false &nbsp;|&nbsp; **Buffered offline:** yes (up to 50 messages)

```json
{
  "device_id": "WROOM_001",
  "signal":    "Speed",
  "value":     85,
  "timestamp": 34521
}
```

| Field | Type | Description |
|-------|------|-------------|
| `device_id` | string | Fixed identifier of this device (`WROOM_001`) |
| `signal` | string | Signal name as received from MCU (e.g. `Speed`, `ENGINE_RPM`) |
| `value` | integer | Signal value; decimal or hex inputs are both normalised to integer |
| `timestamp` | integer | `millis()` at time of publish (ms since boot) |

### Dummy data signals (when `USE_DUMMY_DATA` is defined)

| Signal | Range | Step |
|--------|-------|------|
| `Speed` | 0 – 120 | +5 per tick |
| `ENGINE_RPM` | 800 – 6000 | +200 per tick |
| `THROTTLE` | 0 – 100 | +5 per tick |
| `BRAKE` | 0 – 100 | +10 per tick |
| `STEERING_ANGLE` | −90 – 90 | +15 per tick |

One signal is published per tick (1000 ms default), rotating through the list in order.

## Publish: Device Health → `SmartKit/device_health`

Periodic heartbeat. **Disabled by default** — uncomment `#define PUBLISH_HEALTH` in [src/managers/mqtt_manager.h](src/managers/mqtt_manager.h) to enable.

**QoS:** 0 &nbsp;|&nbsp; **Retain:** false &nbsp;|&nbsp; **Interval:** every 5 s

```json
{
  "device_id":        "WROOM_001",
  "device_type":      "telematics",
  "firmware_version": "1.0.0",
  "timestamp":        60000,
  "status":           "alive",
  "wifi_connected":   true,
  "wifi_rssi":        -62,
  "wifi_ssid":        "iPhone",
  "uptime_ms":        60000,
  "free_heap":        215040,
  "mqtt_buffer_count": 0
}
```

| Field | Type | Description |
|-------|------|-------------|
| `device_id` | string | Fixed device identifier |
| `device_type` | string | Always `"telematics"` |
| `firmware_version` | string | Firmware version string |
| `timestamp` | integer | `millis()` at publish time |
| `status` | string | Always `"alive"` while running |
| `wifi_connected` | bool | Current WiFi connection state |
| `wifi_rssi` | integer | Signal strength in dBm (omitted if not connected) |
| `wifi_ssid` | string | Connected SSID (omitted if not connected) |
| `uptime_ms` | integer | Time since boot in ms |
| `free_heap` | integer | Free heap memory in bytes |
| `mqtt_buffer_count` | integer | Messages currently waiting in the offline buffer |

## Subscribe: `SmartKit/Control`

The device subscribes to this topic on connect. Any message received is written verbatim to the MCU over UART1 TX (GPIO 17), followed by `\r\n`.

No fixed schema is enforced — the payload is forwarded as-is. Typical use: send control commands from a dashboard to the rover MCU.

---

## Offline Buffering

If the MQTT connection drops, outgoing CAN signal messages are held in a circular buffer (capacity: **50 messages**). When the connection is restored, buffered messages are flushed one per scheduler tick (50 ms). If the buffer fills up, the **oldest message is dropped** to make room for new data.

## Configuration

All topic and broker settings live in [src/config/mqtt_config.h](src/config/mqtt_config.h).  
Data source (UART vs dummy) is controlled by the `USE_DUMMY_DATA` macro in [src/config/uart_config.h](src/config/uart_config.h).
